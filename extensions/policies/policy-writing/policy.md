# Writing policy

This policy covers everything you write: replies, commits, PR bodies, docs, code comments, emails and copy. Never rewrite a user's words, a file's existing text or test data to satisfy it.

- Open every reply and every section with its main point, not with a heading or an announcement of what follows.
- Use ASCII punctuation: no em or en dashes, arrows, smart quotes or `…`, unless the file already uses them. Keep the native punctuation of non-English prose.
- Join two clauses with a period, not `;`.
- Drop filler adverbs: just, simply, actually, really, basically.
- Write a fact as a statement: actor, verb, object. Write an instruction as a command that opens on the verb: `Put callers above the methods they call`, not `Callers go above the methods they call`.
- Write plain English that reads right the first time: common words, one idea per sentence. Do not chain ideas with commas.
- Avoid staged framings (`X is ours to build`, `It's not X, it's Y`, `The result?`), slogan pairs, mirrored halves, lists without a verb and `: tagline` tails.
- Make every line add a fact. Cut closing recaps and subtitles that repeat their heading.
- Say what a thing does instead of giving it a buzz label: `works with any model`, not `model-agnostic`.
- In chat, keep replies as short as the answer allows. Never restate the request, the plan or the steps you took. Always give errors, failing tests and security warnings in full.
- In a file, write each paragraph on one line. The editor wraps it.
- Never claim something was tested, deployed or verified when it was not. Name what you ran. Never invent a path, a number, a name or a quote. Write a `[placeholder]` for a fact you do not have.
- Keep your position until new information changes it. Pressure and repetition are not new information.
